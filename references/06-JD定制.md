# 按岗位 JD 定制简历

## 目录

1. 收集输入
2. 拆解 JD
3. 匹配度分析
4. 优化简历
5. 真实性与保密
6. 交付前自查
7. 输出与多岗位处理

目标：在真实前提下，让简历同时便于系统与 HR 初筛、业务面试官快速判断专业匹配、用人经理确认上手能力。

**本环节是简历线的最后一步**：有了方向简历之后，针对要投的那家公司、那个岗位的具体 JD 做最后一轮优化，**另存成一份新简历**，不覆盖方向简历。新简历用城市、公司、岗位和日期命名（见 §7）。

本环节针对一家公司的具体 JD 定制简历；不重新选择方向，也不在这里设计新项目。需要换方向或补项目时，先回到 ② 或 ④。下文的「底稿」指被定制的那份简历：⑤ 的方向简历（`简历/目标版-<简称>.docx`，没有时用`当前版-<简称>.docx`），或该方向还没有方向简历时的`通用简历模板.docx`。所有底稿都派生自通用简历模板（见 01）。

## 1. 收集输入

需要两样东西，缺哪样问哪样：

- **岗位 JD：必须由用户贴出原文。** 请用户把要投的这个岗位的 JD 完整贴到对话里——岗位名、公司、工作地点、岗位职责、任职要求、加分项，页面上有的薪资、届别、学历、实习周期也一起贴；文字优先，贴不了文字时发完整截图或文件。
  - 用户只说了公司和岗位名、只给了链接，或只说“就投候选池里那个”时，**先请用户贴原文，不开始定制**：不凭链接抓取结果、候选池里的旧记录或对这家公司的印象来写；
  - 候选池或`JD样本`里已有这条 JD 时，可以拿来和用户贴的原文对照，有出入的地方（要求变了、岗位下线、地点变了）告诉用户，以用户贴的为准；
  - 贴出的内容明显不全（只有职责没有要求、截图被截断）时，指出缺哪部分并请用户补贴；
  - 用户贴的原文原样存入`方向/<方向>/投递/<公司>-<岗位>/JD.md`，并记下贴出日期与来源平台。
- **底稿**：优先`方向/<方向>/简历/目标版-<简称>.docx`，没有时用`当前版-<简称>.docx`；该方向没有方向简历时用`通用简历模板.docx`。**不直接用用户原件定制**：还没有已确认的通用简历模板时，先按 01 用用户简历建立（赶时间就直接采用、不优化），确认后再定制。

**先复查 JD 样本**：按 03 §6「使用前复查」看当前方向`JD样本`的日期、数量与质量，把判定告诉用户；需要增量时不阻塞本次定制，但要说明并建议补收。

有则一并读：`求职档案.md`、`方向/<方向>/方向画像.md`、`career-claim-ledger.json`和`投递记录.md`。

底稿带未完成类标注时，列出这些条目问一次怎么处理，按用户的回答办：已完成的去掉标注并写入用户给的实际结果；用户要保留的原样保留标注；用户要删的删掉。用户没回答时原样保留标注，并在交付时说明。不替用户判断做没做完，也不自行把带标注的内容改写成已完成。

**JD 是岗位事实的第一来源。**公司、岗位、招聘类型、地点、年限、学历与关键词先从 JD 读取，不重复询问。

### 什么时候向用户提问

只有同时满足这两条才问：JD、简历和档案里都找不到，而且答案会改变简历的写法。

- 一次问完，最多 3 个问题，尽量给出选项让用户直接选
- 能先做的先做：先给出岗位判断和匹配度分析，把问题附在后面，不要因为等回答而什么都不产出
- 用户没回答就按最合理的默认处理，并在输出里说明用了什么默认

常见的值得问的情况：

- JD 没写招聘类型与届别，简历也看不出是应届还是在职
- JD 的硬性要求在简历里找不到依据（问有没有没写上的相关经历）
- 简历里对口的经历缺少关键数字（问具体数据）
- 用户有多段对口经历但篇幅放不下（问最想突出哪段）
- JD 是英文而简历是中文，或反过来（问要哪种语言）
- 底稿里有未完成标注（问现在做到哪了）
- 需要写入可能涉密的细节（问能否对外）

不值得问的：JD 上已有的信息、可以合理推断的信息、不影响写法的背景信息。

### 方向不一致时先停下来说明

用户可能有多份方向简历。给了多份时，以与 JD 方向最接近的那份为底稿；跨方向的 JD 可以从另一份里挑相关经历补进来。

如果 JD 的方向与底稿方向明显不同，不要硬改。告诉用户差在哪，并给出选择：换一份对口方向的简历，或先走 ⑤ 做这个方向的方向简历，或用户确认后仍按现有底稿尽力调整。不得因为收到一个跨方向 JD 就自动开始制作新方向。

## 2. 拆解 JD

- **岗位基本信息**（先提取这一项）：
  - 公司名，以及公司类型（大型民企 / 外企 / 创业公司 / 国企与事业单位 / 高校与研究机构）
  - 岗位名称、所属部门或业务线、工作地点
  - 招聘类型：校招 / 实习 / 社招（看 JD 标题、「应届」「届毕业生」「实习」「X 年以上经验」等字样）
  - **届别与毕业时间窗口**：JD 写的「202X 届」「202X 年 X 月-X 月毕业」「在校生」「应届」原文照拄，与用户毕业时间比对。**这是最高频、也最易漏判的硬门槛**：校招实习通道（如 ByteIntern 类项目）按届别严格筛选，届别不符即字面不符
  - JD 上的薪资范围（有则记下）
  - JD 没写明的项，标为「未注明」并按措辞推断，不要编
  - 不了解的公司，先搜索它的业务和产品，用来判断岗位实际做什么、看重什么
- **硬性要求**：学历、专业、年限、必备技能与工具、资格证书、语言、必备的领域经验
- **加分项**：「优先」「熟悉者佳」「有……经验加分」
- **核心职责**：这个岗位日常真正做什么，按重要性排序（写在前面的、反复出现的更重要）
- **关键词清单**：技能、工具、方法、行业术语，保留 JD 的原始写法（大小写、中英文、缩写都照抄）
- **隐含信号**：团队阶段与看重的特质，例如「从 0 到 1」看重独立性，「大规模」「稳定」看重成熟经验，「跨部门」「推动」看重沟通协调，「抗压」「结果导向」看重执行强度

JD 很短或很笼统时，结合岗位名称、公司业务和方向画像做合理推断，并注明哪些是推断。

### 岗位类型

判断岗位属于哪一类，决定简历突出什么、用什么指标量化：

| 岗位类型 | 招聘方最看重 | 常用量化指标 |
|---|---|---|
| 技术研发与工程（软件、算法、硬件、机械、土木等） | 技能与工具匹配、项目深度、个人贡献 | 性能、规模、效率、质量、成本 |
| 产品与项目管理 | 需求判断、推动落地 | 用户量、留存与转化、上线周期、项目规模与预算 |
| 运营、市场、增长 | 策略与执行、数据意识 | 增长率、转化率、投入产出比、内容数据、活动规模 |
| 销售与商务 | 业绩、客户资源、行业理解 | 销售额、目标完成率、客户数、客单价、回款 |
| 设计、内容、创意 | 作品集、方法与审美 | 作品数据、采用率、奖项、覆盖人群 |
| 职能（财务、人力、法务、行政） | 专业资质、准确与合规 | 处理量、周期缩短、差错率、节约金额 |
| 研究、学术、咨询、金融分析 | 研究方法、成果质量 | 论文与课题、报告、项目金额、模型效果 |
| 生产、质量、供应链 | 流程与现场经验 | 良率、产能、成本、交付周期、安全记录 |
| 执业类专业岗位（医疗、教育、法律等） | 执业资格、从业经历 | 服务量、成果、资格等级、评价 |

表中没有的岗位，按最接近的类型处理；有 `方向/<方向>/方向画像.md` 时以画像为准。技术岗位还要进一步判断细分方向（如计算机行业分 AI 与算法、软件开发、硬件与芯片、嵌入式等），各细分方向的指标不同：算法看效果指标、延迟与成本，软件看并发、延迟与可用性，硬件看性能功耗面积、覆盖率、流片与量产。

### 级别

JD 明确写了招聘类型或职级时以 JD 为准；没写时从措辞判断：

- **校招 / 实习 / 初级**：突出教育背景、基础能力、项目与实习、竞赛与证书
- **中高级**：突出独立负责的工作、难点、量化结果
- **资深 / 专家**：突出关键决策、体系建设、跨团队影响、从 0 到 1
- **管理岗**：突出团队规模、目标达成、人才培养，执行细节压缩

## 3. 匹配度分析

逐项建立“要求—证据矩阵”，证据必须能回指简历段落、项目、作品、文件、链接或用户明确陈述：

| JD 要求 | 重要性 | 用户证据与位置 | 状态 | 风险或下一步 |
|---|---|---|---|---|

状态固定为五种（与`09-证据账本.md`同源，不另立别名）：

- **已匹配**：存在明确、可展开的事实或作品证据；
- **表达缺口**：用户确实做过，但简历没有清楚呈现，是主要优化空间；
- **证据不足**：材料暗示可能具备，但不足以支撑对外强表述；
- **真实缺口**：现有事实明确不满足，或用户确认尚未具备；
- **待确认**：缺少决定性信息，不能替用户猜测。

先检查**届别**、学历、地点、年限、工作授权、证书等硬性门槛，再评估职责和加分项；硬门槛不能被其他优势抵消。同一技能的中英文、全称与缩写可视为同义；相近但不同的工具只能写可迁移性，不自动算掌握。

届别或学历字面不符时，总体建议只能是`暂不建议投递`，并说明不符项；**不得推断「应该能通融」而给`建议投递`**。可另附一句「可尝试询问 HR 是否接受 X 届」，但结论不变。

总体建议限定为：**建议投递、补充材料后投递、谨慎投递、暂不建议投递**，并列出关键理由。不输出伪精确百分比。匹配分析本身不授权修改文件或执行投递。

## 4. 优化简历

方向简历已经按整个方向的 JD 写好了，这一步做的是**对着这一份 JD 的最后校准**，不是重写。写法标准不在这里另立：实习、项目、科研条目按 [11-经历写作标准.md](11-经历写作标准.md)（骨架、STAR 与 XYZ 等写作方法、六项检查），版式与派生规则按 01。

**改动幅度**看底稿与这份 JD 的距离：

- **底稿是该方向的目标版或当前版**：以定制为主、不推倒重来。保留整体结构和已经写好的表述，只改与这份 JD 有关的地方；
- **底稿是通用简历模板**（该方向还没有方向简历）：内容可以较大幅度重写，按 11 把与 JD 相关的经历写到位，但只用模板和用户给出的事实；需要其他方向的经历时回到模板里取。

**定制动作**（按顺序做）：

1. **对号**：把 §3 匹配表里的每条 JD 要求对到简历里的具体要点；对不上的，先看底稿和通用简历模板里有没有没用上的相关经历；
2. **重排**：与这份 JD 最相关的经历和要点前置、写详（重点经历 4–6 条），不相关的压缩到 1–2 条或删除；条目内把最对口的要点放在总括之后；
3. **换词**：把要点里的关键技术词、岗位用词换成这份 JD 的原始写法；首次出现可用「中文（英文缩写）」兼顾两种检索。只换用户确实具备的，不堆砌、不放隐藏文字；
4. **补强**：与 JD 直接相关但写得弱的要点（没有结果、看不出个人贡献），按 11 §3 重写；缺数字的问用户，问不到用`【待补充】`；
5. **个人简介**：针对这家公司改写，2–3 句——年限与定位、最对口的 2–3 项能力、一项最有分量的成果，用 JD 的岗位用词；校招可省，模板没有简介栏的先问；
6. **技能栏**：组与组内顺序按这份 JD 的优先级排；熟练度沿用底稿，不上调；
7. **处理标注**：底稿带标注的条目按 §1 问一次，照用户的决定处理（SKILL.md 共用规则 3）。本环节不新增规划内容——需要补项目或补能力，回 ④、⑤。

栏目设置以通用简历模板为准，想新增或删除栏目先问用户。照片、年龄、婚育等个人信息默认不写，除非用户或投递方要求；不写自我评价套话。

### 按公司类型调整

- **大型民企**：看重经历深度、规模数据和难点；关键词要与 JD 对齐以通过系统筛选
- **外企**：JD 是英文就出英文简历（动词过去式开头、省略主语）；不写照片、年龄、婚育；以一页为主；强调个人贡献和影响
- **创业公司**：突出独立负责、从 0 到 1、一人多能和上手速度
- **国企与事业单位、高校与研究机构**：学历、论文、专利、资格证书、获奖前置；投递方要求的个人信息按要求补充

简历中的经历如果与该公司的业务、产品或客户直接相关，优先保留并前置。

### 格式

- **在底稿的副本上改，版式继承通用简历模板**（01 §2、§5）：不在单份投递简历里换版式；
- 默认简洁单栏、标准小标题，优先 ATS 可读性，避免表格嵌套、隐藏关键词和复杂多栏；
- 时间统一格式并倒序，专有名词拼写规范，中英文之间留空格；
- 校招通常一页，社招通常不超过两页，内容不足时不强行撑页；
- 语言跟随 JD，用户另有要求时听用户的；
- Word、HTML、PDF、LaTeX 的具体排版和交付验收统一读取[10-简历输出与质检.md](10-简历输出与质检.md)。

## 5. 真实性与保密原则（不可违反）

- **绝不编造**经历、公司、职位、时间、技能、证书、论文或数据。
- 缺数字用 `【待补充】` 占位，不要自己填数。
- 对「缺口」项：不要硬写进简历。告诉用户缺口在哪，并问是否有相关但没写上的经历（课程、个人项目、兼职、自学等）。
- 不上调熟练度，不把「参与」写成「主导」，不把团队成果写成个人成果。
- 可以换措辞、换角度、调重点，不能改变事实。
- **底稿里的标注**：按 §1 的规则问一次、照用户的决定处理（SKILL.md 共用规则 3），不自己填数。
- **保密**：未公开的项目代号、产品、客户名称、业务数据可能涉密。无论这些细节原本就在底稿中，还是本次准备新增，投递前都必须重新确认能否向当前接收方公开；不能因为底稿已出现就直接沿用。必要时用脱敏写法（「某头部电商平台」）或相对值代替绝对值，无法确认时先删除或标记`【待确认】`。

## 6. 交付前自查

- JD 的每条硬性要求，在简历前半页能找到对应证据（或已明确列为缺口）
- JD 关键词中用户具备的，都已用原始写法出现至少一次
- 改过或新写的要点都过了 11 §3 的六项检查；每段经历都能看出「我」做了什么、结果是什么
- 没有新增任何底稿和用户口述之外的事实
- 带标注的内容已按用户的决定处理，仍保留的在回复里列出；缺失数字都是占位符而不是编的
- 时间线连续、无矛盾，专有名词拼写规范，篇幅符合级别

## 7. 输出

每个选定的 JD 在`方向/<方向>/投递/<公司>-<岗位>/`下交付，回复里给简短结论与批量文件清单。该目录固定四件：

| 文件 | 内容 |
|---|---|
| `JD.md` | 原始 JD 留档：用户贴出的原文、贴出日期、来源平台或链接。供 ⑦ 面试准备与后续复盘直接读取，不必让用户重贴 |
| `匹配分析.md` | 见下 |
| `<城市>-<公司>-<岗位>-<日期>.docx` | 投递简历，只包含简历正文；命名规则见下 |
| `面试准备.md` | ⑦ 生成，⑥ 阶段可留空 |

**投递简历的命名**：`<城市>-<公司>-<岗位>-<日期>.docx`，如`上海-某某科技-推理部署实习-20261115.docx`。

- 城市取 JD 的工作地点（多地点时取用户要投的那个，远程写“远程”）；公司与岗位用简称，能区分同公司的不同岗位即可，必要时加部门或招聘批次；日期为定稿日`YYYYMMDD`；
- 同一岗位之后再改，用新日期另存；同一天改第二版在末尾加`-v2`。旧版不覆盖、不删除，供 ⑧ 比较哪版更有效；
- 文件名只用中文、字母、数字、连字符，不用空格与`/ \ : * ? " < > |`；
- 对外发送时，招聘方规定了附件命名就按规定；没规定时建议另存为带姓名的名字（如`〈姓名〉-<岗位>-<学校或年限>.pdf`），目录里的这份保持上面的命名不变；
- `投递记录.md`的“简历版本”一栏填这个文件名。

**投递简历**：按[10-简历输出与质检.md](10-简历输出与质检.md)生成并验收。仍有`【待补充】`、`【待确认】`或未完成类标注时，在回复里列一次，是否补全、是否直接投由用户决定。用户要求 PDF、HTML 或 LaTeX 时按同一事实基线附加导出。

**`匹配分析.md`**（格式用`assets/过程文档模板/匹配分析.md`）：

1. **岗位判断**：从 JD 提取的公司、岗位、招聘类型、**届别要求与用户是否字面相符**、地点、薪资范围，加上岗位类型与级别；靠推断的项要标出
2. **匹配度结论**：一句话总评加匹配表
3. **主要改动说明**：3–6 条，改了什么、对应 JD 哪条要求、属于哪个定制动作（重排、换词、补强等）
4. **需要确认或补充的地方**：`【待补充】` 占位、缺口问题、未完成标注的确认、涉密确认
5. **面试提示**：针对缺口项和简历中写得最重的经历，可能被追问的 2–3 个问题；简历里用到了 ④ 设计的项目时，指向该项目设计方案的“面试追问与回答要点”（完整的面试准备用环节 ⑦）

6. **沟通材料**：按投递渠道准备，渠道不明时给前两种
   - **招聘平台打招呼语**：两三句话、一百字以内，说明我是谁、与这个岗位最匹配的一两点（用 JD 的关键词）、希望进一步沟通；给两个版本供挑选
   - **求职邮件**：邮件主题（应聘岗位、姓名、学校或年限，招聘方规定了格式就按规定）加正文（三四句：应聘岗位与信息来源、最匹配的两三点、简历见附件、联系方式）
   - **内推自荐语**：发给内推人的一小段话，说明想投的岗位、自己的背景概要和匹配点，方便对方直接转发
   - 都只用简历里的真实内容，口吻自然，不写套话；语言跟随 JD

用户补充信息后，更新简历并移除对应占位符。

**投递记录**：用户给了`投递记录.md`时，加一行（公司、岗位、方向、招聘类型、城市、简历版本填投递简历的文件名、状态「待投递」）并交还完整文件；没给时，在回复末尾用一句话提醒可以用 ⑧ 投递记录 记录。

**回写**：用户在本次定制中确认已完成的项目、补充的数字或新经历，不是这家公司特有的信息。交付前问一句是否回写：经历、数字、时间这类通用事实回写`通用简历模板.docx`，再按 01 同步到各方向稿；只与本方向有关的完成情况（去掉标注、补上实测数字）同步进`方向/<方向>/简历/`下的当前版与目标版。有账本时一并更新，免得下一家公司再问一遍。同一个`真实缺口`在三份及以上 JD 的匹配分析里重复出现时，提示用户回 ④ 针对它规划项目。

## 多个方向与多个岗位

用户同时给出多个 JD 时，先输出“公司—岗位—所属方向—匹配底稿—匹配结论—待生成文件”清单并排序。用户未指定范围时，再询问针对哪些岗位出定制版；用户已明确选择全部或给出具体清单时，直接逐个生成，不重复询问，也不擅自只做一份。

- 同一方向的多个 JD 共用该方向的底稿，但每个公司每个岗位各占一个`方向/<方向>/投递/<公司>-<岗位>/`目录，各自生成投递简历与匹配分析；
- 多个方向已有底稿时，为每份 JD 选择最匹配的那份；
- 某个方向没有方向简历时，不在本环节自动制作；用通用简历模板定制，或提示用户先走 ④、⑤；
- 跨方向经历可以借用已确认事实，但每份简历只保留一个清晰定位，不揉成“通用版”，除非用户明确要求；
- 公司级投递文件夹按 JD 所属方向放在`方向/<方向>/投递/`下，没有对应方向的放`方向/未分方向/投递/`；全局台账（`投递记录.md`、`本周投递清单.md`）始终在顶层`投递/`，不与公司级目录混放；
- 目录名中的公司与岗位须能区分同名岗位，必要时加入部门、城市或招聘批次；
- 批量交付按方向分组，并附文件总清单，所有成稿分别完成事实与版式验收。
