## 1. 定位与输入

本环节把通用简历改造成**当前已确认方向**的可复用底稿，完成“JD 要求—用户证据—补缺口行动—最终目标简历—项目设计方案”的闭环。多个方向只排队，不并行制作，也不把多个方向揉成一份。

必需输入：

- 通用简历或等价的经历说明；附件须完整读取；
- 当前要制作的**一个方向**，优先读取`求职档案.md`和`方向报告.md`；
- 用户提供的当前方向 JD 相关材料，如 JD 文本、完整截图、链接或岗位要求；
- 时间预算、每周可投入时间、校招或社招；
- 用户明确确认“现在制作这个方向”。

有则读取：技术栈资料、`career-claim-ledger.json`、设备与数据条件、已有项目代码或作品。材料没有答案时才提问，最多 3 个；用户不回答资源预算时，可暂按“4–8 周、每周 10–15 小时、仅个人电脑”并明确标注假设。

只有具体公司 JD 时也可从本环节开始，但确认制作后应补充同方向的代表性 JD，避免项目只适用于一家公司。用户还没选方向时，先建议①方向选择。项目完成后更新已有方向时，复用该方向已有 JD 材料，不重复要求用户提供。

### 启动门禁与多方向处理

- 未提供当前方向的 JD 相关材料时，只说明需要哪些材料并等待，不开始完整调研、项目设计或目标简历制作；
- 材料已提供但用户尚未明确确认制作时，只列材料摘要、待交付文件和预计工作量，请用户确认，不提前生成；
- 用户选定多个方向或一次提供多个方向的材料时，先确认制作顺序，**本轮仍只制作当前一个方向**；其他方向仅记录“待提供材料／待确认／排队中”状态；
- 当前方向交付`方向画像-〈方向〉.md`、差距分析、`最终目标简历-〈方向〉.docx`和项目设计方案后停止，不自动开始下一个方向；下一个方向须由用户再次明确确认；
- 求职档案和证据账本共享，但按方向记录材料、确认状态、文件和项目进度；
- 同一个真实项目可支持多个方向，只维护一份实际实施进度；后续方向确认制作时，再调整简历重点和方向专属任务。

## 2. 调研方向要求

先复用三个月内且来源清楚的`方向报告.md`和`方向画像-〈方向〉.md`，只补查缺失细节；过期或样本过少时重新调研。

- 优先使用用户提供的 JD，再补充 8–15 份同方向真实 JD；目标公司、不同规模公司和校招/社招类型要有代表性。
- 使用宿主浏览器或搜索工具读取当前信息，记录公司、岗位、链接或材料名、日期。
- 无法访问招聘平台时，请用户复制 8–10 份 JD 或提供完整截图，同时先用已有资料推进。
- 不将单个 JD 的个性化要求误判为整个方向的必备要求。

形成`方向画像-〈方向〉.md`：

| 分类 | 内容 |
|---|---|
| 必备 | 多数样本明确要求的基础能力、工具、学历或证书 |
| 高频 | 约半数样本出现的技能、经验和业务场景 |
| 加分 | 能形成区分度的成果、作品、竞赛、开源或领域经验 |
| 项目期望 | 招聘方希望候选人做过的任务、规模和深度 |
| 原始用词 | JD 中常见的技能、工具和岗位术语写法 |

注明样本数量、覆盖公司、检索日期和来源。样本不足时明确局限。

## 3. 差距与项目适配分析

逐项对照方向画像与用户材料：

| 方向要求 | 重要程度 | 用户证据 | 状态 | 补法 |
|---|---|---|---|---|
|  |  |  | 已具备／表达缺口／证据不足／真实缺口／待确认 |  |

项目判断不以“有没有项目”为标准，而以“能否支撑目标 JD”为标准：

1. **项目合适，表达较弱**：保留事实，按 JD 重写个人动作、技术细节和结果，不新增项目。
2. **项目部分合适**：优先扩展已有项目，增加真实模块、架构优化、测试、数据分析或作品案例。
3. **项目不合适**：方向不符、技术过旧、深度不足、只有课程作业或无法说清个人贡献时，不为利用旧项目而硬凑，进入新项目设计。
4. **没有项目**：直接进入新项目设计。
5. **项目补不了的缺口**：学历、年限、法定资格、量产经历等如实说明，不假装项目能解决。

社招以工作经历和真实业务成果为主；只有转方向或存在明显能力缺口时才设计新项目。校招和转方向用户可将项目作为重点。

## 4. 原创项目反向设计

从代表性 JD 反向确定项目，而不是先想一个项目再硬贴关键词。每个项目必须满足：

- **对口**：明确覆盖哪些必备、高频或加分要求；
- **真实场景**：解决真实问题，尽量使用真实数据、真实用户或用户专业背景；
- **可做**：符合时间、设备、知识和数据预算，有最小可交付版本；
- **有深度**：至少有一个能展开讨论的方案选择、性能问题、业务难点或失败路径；
- **可测量**：事先确定基线、指标、测试方法和数据来源；
- **可验证**：最终能拿出代码、演示、报告、作品、测试记录、用户反馈或实物；
- **有区分度**：避免纯教程复刻和同质化商城、外卖、图书管理等项目，除非有明确业务创新或工程深度。

数量通常 1–3 个，优先一个做深。先列出候选项目的“目标、覆盖缺口、路线、周期、最小交付”，让用户确认；用户要求直接出完整初稿时，选择最合理组合并说明理由。

非技术岗位可采用真实运营账号、用户调研、竞品分析、活动策划、行业研究、数据分析、作品集案例、实务案例等形式，不强行使用软件开发项目。

## 5. 开源项目二次开发

项目不合适或没有项目时，可以选择活跃开源项目进行实质性二次开发。高 Star 只能作为线索，不能替代适配判断。

### 选择标准

按“JD 相关度 → 可改性 → 可验证性 → 维护与许可 → 星标与社区”评估：

- 技术栈、业务场景和目标 JD 对口；
- 能在预算内安装、运行、理解和修改；
- 架构与复杂度适合用户，不选择无法讲清的庞大项目；
- 官方仓库仍在维护，文档、Issue、提交和发布状态正常；
- 许可证允许学习、修改和预期用途，保留版权与许可声明；
- 有明确的增量空间、测试方式和可展示交付物。

记录仓库官方链接、检索日期、Star 等社区指标的快照、最近维护情况、许可证和选择理由。无法核实时标记待确认，不编造数据。

### 合格增量

- 新增与目标岗位相关的完整模块；
- 重构核心流程并解决可复现的问题；
- 做有基线和复测数据的性能、可靠性或可用性优化；
- 补充有意义的自动化测试、 observability、部署或数据治理；
- 修复真实 Issue，提交有质量的 PR；
- 基于原项目完成明确的新业务场景或作品案例。

仅 Fork、跑通 Demo、跟随教程、改文案或换 UI，不构成有区分度的项目亮点。未合并 PR 写“已提交，协作中”，不得写“已被采用”；只有用户实际完成的修改才能写成个人贡献。

## 6. 最终目标简历

确定路线后，**先生成最终目标简历，再开始项目实施**。它让用户先看到完成后的求职目标，而不是等项目全部结束才第一次写简历。

### 内容

- 按目标方向重写个人定位和已有经历；
- 重排技能、教育、实习、项目与奖项；
- 为新项目写 3–5 条高密度要点：背景与目标、个人任务、关键方法、技术难点、验证结果；
- 保留计划中的技术栈和指标，但分别标注`【计划学习】`和`【待实测】`；
- 项目标题标`【未完成】`，开始后改为`【进行中】`；
- 文首注明：“这是最终目标简历，含规划内容，带标注部分完成前不能用于投递。”

完整技术方案、实施步骤和面试题放入项目设计方案，不把简历写成项目说明书。已有经历中的缺口继续使用`【待补充】`或`【待确认】`。

### 两种当前版本

- `最终目标简历-〈方向〉.docx`：包含规划项目，用于指导实施；
- 用户需要立即投递时，另出`当前简历-〈方向〉.docx`：删除未开始项目和未掌握技能，进行中的项目只写已完成且能证明的部分。

生成和验收文件时读取[07-简历输出与质检.md](07-简历输出与质检.md)。

## 7. 项目设计方案

每个新项目生成`项目设计方案-〈项目名〉.md`，与对应方向的最终目标简历同时交付，采用以下结构：

```markdown
# 项目名称

## 一句话介绍
解决什么问题，服务什么场景。

## 为什么做
对应方向画像和 JD 的具体要求。

## 路线与来源
原创设计，或开源仓库、版本、许可证、二次开发边界。

## 技术与工具
标出已有能力和【计划学习】内容。

## 范围
- 最小可交付版本
- 进阶项
- 明确不做的事项

## 里程碑
按周列出目标、任务、产出物和预计小时数。

## 难点与方案
列出候选方案、取舍、失败路径和验证方法。

## 指标与测量
基线、指标、数据、测试环境、复测方法；目标值只写在这里。

## 交付物
代码、文档、演示、测试、作品、报告、PR 或其他证据。

## 验收标准
达到什么条件才可移除简历标注。

## 写进最终目标简历的样子
与目标简历一致，数字保留【待实测】。

## 面试追问
列出完成后应能回答的 5–8 个问题。

## 参考资料
只列已确认存在的官方文档、论文或仓库。
```

计划要具体到能开工，但不替用户虚构完成过程。项目实施中的源码学习、真实 Issue、实验记录和交付证据应持续保存。

## 8. 项目实施后更新简历

这不是新的求职阶段。用户按照项目设计方案实施，之后带着实际成果回到本环节更新：

1. 对照里程碑和验收标准核实实际完成范围；
2. 根据代码、演示、测试、报告、作品、PR 或用户说明，确认个人动作和真实结果；
3. 更新证据账本中的候选表述、来源、确认状态和面试细节；
4. 没做的内容删除，技术栈按实际填写，结果只写实测值；
5. 部分完成则标`【进行中】`，只写已完成部分；
6. 全部核实后移除标注，生成可复用投递底稿`方向简历-〈方向〉.docx`；
7. 同一项目用于多个方向时，只更新一次事实与进度，再分别更新各方向简历的措辞和重点；
8. 再按[07-简历输出与质检.md](07-简历输出与质检.md)验收。

## 9. 交付清单

完整执行时，**本轮只交付当前已确认方向的材料**：

1. `方向画像-〈方向〉.md`；
2. 该方向的差距与项目适配分析；
3. `最终目标简历-〈方向〉.docx`，需要立即投递时附当前版；
4. 该方向每个新项目一份`项目设计方案-〈项目名〉.md`，与最终目标简历同时交付；
5. 开源路线附仓库选择、许可证与二次开发边界；
6. 项目完成后更新并交付`方向简历-〈方向〉.docx`。

所有方向共用一份更新后的`求职档案.md`，分别记录 JD 材料、确认状态、文件、项目状态、计划日期与更新记录；按需创建或更新共享的`career-claim-ledger.json`。本轮交付附“当前方向—目标简历—项目设计方案—项目状态”清单，以及“其他方向—待提供材料／待确认／排队中”队列。当前方向交付后即停止，等待用户确认是否制作下一个方向。
