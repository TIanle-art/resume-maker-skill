# 按岗位 JD 定制简历

## 目录

1. 收集输入
2. 拆解 JD
3. 匹配度分析
4. 优化简历
5. 真实性与保密
6. 交付前自查
7. 输出与多岗位处理

目标：在真实前提下，让简历同时便于系统与 HR 初筛、业务面试官快速判断专业匹配、用人经理确认上手能力。

本环节针对一家公司的具体 JD 定制简历；不重新选择方向，也不在这里设计新项目。需要换方向或补项目时，先回到 ① 或 ②。下文的「底稿」指被定制的那份简历：② 的最终目标简历、用户自己的现有简历，或`通用简历.docx`。

## 1. 收集输入

需要两样东西，缺哪样问哪样：

- **岗位 JD**：文本、截图、文件或链接均可；链接无法访问时请用户直接提供文本。
- **底稿**：优先`方向/<方向>/最终目标简历.docx`；没有时使用用户现有的 Word、PDF、图片或文本简历，或`通用简历.docx`，附件须完整读取。用户什么简历都没有时，先按 02 §3 建通用简历。

有则一并读：`求职档案.md`、`方向/<方向>/方向画像.md`、`career-claim-ledger.json`和`投递记录.md`。

底稿带未完成类标注时，列出这些条目问一次怎么处理，按用户的回答办：已完成的去掉标注并写入用户给的实际结果；用户要保留的原样保留标注；用户要删的删掉。用户没回答时原样保留标注，并在交付时说明。不替用户判断做没做完，也不自行把带标注的内容改写成已完成。

**JD 是岗位事实的第一来源。**公司、岗位、招聘类型、地点、年限、学历与关键词先从 JD 读取，不重复询问。

### 什么时候向用户提问

只有同时满足这两条才问：JD、简历和档案里都找不到，而且答案会改变简历的写法。

- 一次问完，最多 3 个问题，尽量给出选项让用户直接选
- 能先做的先做：先给出岗位判断和匹配度分析，把问题附在后面，不要因为等回答而什么都不产出
- 用户没回答就按最合理的默认处理，并在输出里说明用了什么默认

常见的值得问的情况：

- JD 没写招聘类型，简历也看不出是应届还是在职
- JD 的硬性要求在简历里找不到依据（问有没有没写上的相关经历）
- 简历里对口的经历缺少关键数字（问具体数据）
- 用户有多段对口经历但篇幅放不下（问最想突出哪段）
- JD 是英文而简历是中文，或反过来（问要哪种语言）
- 底稿里有未完成标注（问现在做到哪了）
- 需要写入可能涉密的细节（问能否对外）

不值得问的：JD 上已有的信息、可以合理推断的信息、不影响写法的背景信息。

### 方向不一致时先停下来说明

用户可能有多份方向简历。给了多份时，以与 JD 方向最接近的那份为底稿；跨方向的 JD 可以从另一份里挑相关经历补进来。

如果 JD 的方向与底稿方向明显不同，不要硬改。告诉用户差在哪，并给出选择：换一份对口方向的简历，或先走 ② 做这个方向的目标简历，或用户确认后仍按现有底稿尽力调整。不得因为收到一个跨方向 JD 就自动开始制作新方向。

## 2. 拆解 JD

- **岗位基本信息**（先提取这一项）：
  - 公司名，以及公司类型（大型民企 / 外企 / 创业公司 / 国企与事业单位 / 高校与研究机构）
  - 岗位名称、所属部门或业务线、工作地点
  - 招聘类型：校招 / 实习 / 社招（看 JD 标题、「应届」「届毕业生」「实习」「X 年以上经验」等字样）
  - JD 上的薪资范围（有则记下）
  - JD 没写明的项，标为「未注明」并按措辞推断，不要编
  - 不了解的公司，先搜索它的业务和产品，用来判断岗位实际做什么、看重什么
- **硬性要求**：学历、专业、年限、必备技能与工具、资格证书、语言、必备的领域经验
- **加分项**：「优先」「熟悉者佳」「有……经验加分」
- **核心职责**：这个岗位日常真正做什么，按重要性排序（写在前面的、反复出现的更重要）
- **关键词清单**：技能、工具、方法、行业术语，保留 JD 的原始写法（大小写、中英文、缩写都照抄）
- **隐含信号**：团队阶段与看重的特质，例如「从 0 到 1」看重独立性，「大规模」「稳定」看重成熟经验，「跨部门」「推动」看重沟通协调，「抗压」「结果导向」看重执行强度

JD 很短或很笼统时，结合岗位名称、公司业务和方向画像做合理推断，并注明哪些是推断。

### 岗位类型

判断岗位属于哪一类，决定简历突出什么、用什么指标量化：

| 岗位类型 | 招聘方最看重 | 常用量化指标 |
|---|---|---|
| 技术研发与工程（软件、算法、硬件、机械、土木等） | 技能与工具匹配、项目深度、个人贡献 | 性能、规模、效率、质量、成本 |
| 产品与项目管理 | 需求判断、推动落地 | 用户量、留存与转化、上线周期、项目规模与预算 |
| 运营、市场、增长 | 策略与执行、数据意识 | 增长率、转化率、投入产出比、内容数据、活动规模 |
| 销售与商务 | 业绩、客户资源、行业理解 | 销售额、目标完成率、客户数、客单价、回款 |
| 设计、内容、创意 | 作品集、方法与审美 | 作品数据、采用率、奖项、覆盖人群 |
| 职能（财务、人力、法务、行政） | 专业资质、准确与合规 | 处理量、周期缩短、差错率、节约金额 |
| 研究、学术、咨询、金融分析 | 研究方法、成果质量 | 论文与课题、报告、项目金额、模型效果 |
| 生产、质量、供应链 | 流程与现场经验 | 良率、产能、成本、交付周期、安全记录 |
| 执业类专业岗位（医疗、教育、法律等） | 执业资格、从业经历 | 服务量、成果、资格等级、评价 |

表中没有的岗位，按最接近的类型处理；有 `方向/<方向>/方向画像.md` 时以画像为准。技术岗位还要进一步判断细分方向（如计算机行业分 AI 与算法、软件开发、硬件与芯片、嵌入式等），各细分方向的指标不同：算法看效果指标、延迟与成本，软件看并发、延迟与可用性，硬件看性能功耗面积、覆盖率、流片与量产。

### 级别

JD 明确写了招聘类型或职级时以 JD 为准；没写时从措辞判断：

- **校招 / 实习 / 初级**：突出教育背景、基础能力、项目与实习、竞赛与证书
- **中高级**：突出独立负责的工作、难点、量化结果
- **资深 / 专家**：突出关键决策、体系建设、跨团队影响、从 0 到 1
- **管理岗**：突出团队规模、目标达成、人才培养，执行细节压缩

## 3. 匹配度分析

逐项建立“要求—证据矩阵”，证据必须能回指简历段落、项目、作品、文件、链接或用户明确陈述：

| JD 要求 | 重要性 | 用户证据与位置 | 状态 | 风险或下一步 |
|---|---|---|---|---|

状态固定为五种（与`06-证据账本.md`同源，不另立别名）：

- **已匹配**：存在明确、可展开的事实或作品证据；
- **表达缺口**：用户确实做过，但简历没有清楚呈现，是主要优化空间；
- **证据不足**：材料暗示可能具备，但不足以支撑对外强表述；
- **真实缺口**：现有事实明确不满足，或用户确认尚未具备；
- **待确认**：缺少决定性信息，不能替用户猜测。

先检查学历、地点、年限、工作授权、证书等硬性门槛，再评估职责和加分项；硬门槛不能被其他优势抵消。同一技能的中英文、全称与缩写可视为同义；相近但不同的工具只能写可迁移性，不自动算掌握。

总体建议限定为：**建议投递、补充材料后投递、谨慎投递、暂不建议投递**，并列出关键理由。不输出伪精确百分比。匹配分析本身不授权修改文件或执行投递。

## 4. 优化简历

**改动幅度原则**：看底稿与这份 JD 的距离。

- **底稿已对口**（该方向的目标简历）：以定制为主、不推倒重来。保留整体结构和已经写好的表述，只改与这份 JD 有关的地方；
- **底稿是通用简历或其他方向的简历**：内容可以较大幅度重写（重选经历、重写要点、重排技能），但仍只用底稿和用户给出的事实，版式仍按下面的格式规则保留；
- 主要动作是：调整经历和要点的顺序与详略、把措辞和关键词对齐到这份 JD、针对这家公司改写个人简介、重排技能栏
- 底稿里某条写得弱（没有结果、看不出个人贡献）且与 JD 相关时才重写，并在改动说明里标出

具体标准（用户有原简历时，栏目设置以原简历为准；下面关于栏目顺序、个人简介和照片的标准只在重建简历时直接适用，想新增或删除栏目先问用户）：

- **结构**：基本信息 → 个人简介 → 工作或实习经历 → 项目经历 → 教育背景（校招前置）→ 专业技能 → 论文、专利、竞赛、证书、作品集（有则写，对口则前置）。底稿结构合理时不动。
- **个人简介**：2–3 句，结构为「年限与定位」加「最对口的 2–3 项能力」加「一项最有分量的成果」，直接使用 JD 的岗位用词。校招可省。
- **顺序与取舍**：与这份 JD 最相关的经历前置、写详（3–5 条要点），不相关的压缩到 1–2 条或删除。很久以前或已过时的经历压缩，除非正好对口。
- **要点写法**：「强动词 + 做了什么（含关键技能）+ 量化结果」。去掉「负责」「参与」「协助」这类看不出贡献的说法；确实只是参与的，写清参与的具体部分。明确「我」做了什么，与团队成果区分开。每条一到两行。
- **量化**：按岗位类型表里的指标来写。简历里没有数字时用 `【待补充：如 提升了多少%】` 占位并集中询问。
- **关键词融入**：用 JD 的原始写法写进经历描述和技能栏；经历里出现比只在技能栏出现更有说服力；首次出现可用「中文（英文缩写）」兼顾两种检索；只融入用户确实具备的；禁止堆砌或隐藏文字。
- **技能栏**：分组写，组和组内的顺序都按 JD 优先级排。熟练度用词诚实且有区分，不确定时沿用底稿的熟练度，不擅自上调。
- **不写**：自我评价套话（「吃苦耐劳」「学习能力强」）、与岗位无关的通用技能；照片、年龄、婚育等个人信息默认不写，除非用户或投递方要求。

改写示例（仅示意写法，数字必须来自用户）：

- 原：负责公众号运营
  改：独立运营【账号名】公众号，策划并撰写【待补充】篇推文，粉丝由【待补充】增至【待补充】，平均阅读量提升【待补充】%
- 原：参与后端服务开发
  改：设计并实现订单查询服务的多级缓存，接口延迟由【待补充】ms 降至【待补充】ms，支撑峰值【待补充】次每秒请求
- 原：协助完成月度结账
  改：独立完成【待补充】家子公司的月度结账与合并报表，结账周期由【待补充】天缩短至【待补充】天

### 按公司类型调整

- **大型民企**：看重经历深度、规模数据和难点；关键词要与 JD 对齐以通过系统筛选
- **外企**：JD 是英文就出英文简历（动词过去式开头、省略主语）；不写照片、年龄、婚育；以一页为主；强调个人贡献和影响
- **创业公司**：突出独立负责、从 0 到 1、一人多能和上手速度
- **国企与事业单位、高校与研究机构**：学历、论文、专利、资格证书、获奖前置；投递方要求的个人信息按要求补充

简历中的经历如果与该公司的业务、产品或客户直接相关，优先保留并前置。

### 格式

- **在底稿的副本上改，不套模板**：保留底稿原有的字体、配色、照片、栏目标题和布局，以改内容为主，结构只做少量调整（顺序、条目增删）；要增删整个栏目或换版式时先征得同意。底稿无法编辑时才用默认 Word 样式重建；
- 默认简洁单栏、标准小标题，优先 ATS 可读性，避免表格嵌套、隐藏关键词和复杂多栏；
- 时间统一格式并倒序，专有名词拼写规范，中英文之间留空格；
- 校招通常一页，社招通常不超过两页，内容不足时不强行撑页；
- 语言跟随 JD，用户另有要求时听用户的；
- Word、HTML、PDF、LaTeX 的具体排版和交付验收统一读取[07-简历输出与质检.md](07-简历输出与质检.md)。

## 5. 真实性与保密原则（不可违反）

- **绝不编造**经历、公司、职位、时间、技能、证书、论文或数据。
- 缺数字用 `【待补充】` 占位，不要自己填数。
- 对「缺口」项：不要硬写进简历。告诉用户缺口在哪，并问是否有相关但没写上的经历（课程、个人项目、兼职、自学等）。
- 不上调熟练度，不把「参与」写成「主导」，不把团队成果写成个人成果。
- 可以换措辞、换角度、调重点，不能改变事实。
- **底稿里的未完成标注**：按 §1 的规则问一次、照用户的决定处理。用户说已完成的，写入其给出的实际结果；没有实际数字时保留`【待实测】`或`【待补充】`，不自己填数。
- **保密**：未公开的项目代号、产品、客户名称、业务数据可能涉密。无论这些细节原本就在底稿中，还是本次准备新增，投递前都必须重新确认能否向当前接收方公开；不能因为底稿已出现就直接沿用。必要时用脱敏写法（「某头部电商平台」）或相对值代替绝对值，无法确认时先删除或标记`【待确认】`。

## 6. 交付前自查

- JD 的每条硬性要求，在简历前半页能找到对应证据（或已明确列为缺口）
- JD 关键词中用户具备的，都已用原始写法出现至少一次
- 每段经历都能看出「我」做了什么、结果是什么
- 没有新增任何底稿和用户口述之外的事实
- 带标注的内容已按用户的决定处理，仍保留的在回复里列出；缺失数字都是占位符而不是编的
- 时间线连续、无矛盾，专有名词拼写规范，篇幅符合级别

## 7. 输出

每个选定的 JD 在`投递/<方向>/<公司>-<岗位>/`下交付，回复里给简短结论与批量文件清单。该目录固定四件：

| 文件 | 内容 |
|---|---|
| `JD.md` | 原始 JD 留档：来源链接、抓取日期、岗位基本信息原文。供 ④ 面试准备与后续复盘直接读取，不必让用户重贴 |
| `匹配分析.md` | 见下 |
| `定制简历-v1.docx` | 只包含简历正文；同一岗位改第二版时新增`-v2`，不覆盖旧版 |
| `面试准备.md` | ④ 生成，③ 阶段可留空 |

**`定制简历-v{n}.docx`**：按[07-简历输出与质检.md](07-简历输出与质检.md)生成并验收。仍有`【待补充】`、`【待确认】`或未完成类标注时，在回复里列一次，是否补全、是否直接投由用户决定。用户要求 PDF、HTML 或 LaTeX 时按同一事实基线附加导出。

**`匹配分析.md`**：

1. **岗位判断**：从 JD 提取的公司、岗位、招聘类型、地点、薪资范围，加上岗位类型与级别；靠推断的项要标出
2. **匹配度结论**：一句话总评加匹配表
3. **主要改动说明**：3–6 条，改了什么、对应 JD 哪条要求
4. **需要确认或补充的地方**：`【待补充】` 占位、缺口问题、未完成标注的确认、涉密确认
5. **面试提示**：针对缺口项和简历中写得最重的经历，可能被追问的 2–3 个问题（完整的面试准备用环节 ④ 面试准备）

6. **沟通材料**：按投递渠道准备，渠道不明时给前两种
   - **招聘平台打招呼语**：两三句话、一百字以内，说明我是谁、与这个岗位最匹配的一两点（用 JD 的关键词）、希望进一步沟通；给两个版本供挑选
   - **求职邮件**：邮件主题（应聘岗位、姓名、学校或年限，招聘方规定了格式就按规定）加正文（三四句：应聘岗位与信息来源、最匹配的两三点、简历见附件、联系方式）
   - **内推自荐语**：发给内推人的一小段话，说明想投的岗位、自己的背景概要和匹配点，方便对方直接转发
   - 都只用简历里的真实内容，口吻自然，不写套话；语言跟随 JD

用户补充信息后，更新简历并移除对应占位符。

**投递记录**：用户给了`投递记录.md`时，加一行（公司、岗位、方向、招聘类型、城市、简历版本如`v1`、状态「待投递」）并交还完整文件；没给时，在回复末尾用一句话提醒可以用 ⑤ 投递记录 记录。

**回写**：用户在本次定制中确认已完成的项目、补充的数字或新经历，不是这家公司特有的信息。交付前问一句是否同步进`方向/<方向>/最终目标简历.docx`（去掉对应标注、补上实测数字），有账本时一并更新，免得下一家公司再问一遍。同一个`真实缺口`在三份及以上 JD 的匹配分析里重复出现时，提示用户回 ② 针对它规划项目。

## 多个方向与多个岗位

用户同时给出多个 JD 时，先输出“公司—岗位—所属方向—匹配底稿—匹配结论—待生成文件”清单并排序。用户未指定范围时，再询问针对哪些岗位出定制版；用户已明确选择全部或给出具体清单时，直接逐个生成，不重复询问，也不擅自只做一份。

- 同一方向的多个 JD 共用该方向的底稿，但每个公司每个岗位各占一个`投递/<方向>/<公司>-<岗位>/`目录，各自生成定制简历与匹配分析；
- 多个方向已有底稿时，为每份 JD 选择最匹配的那份；
- 某个方向没有目标简历时，不在本环节自动制作；用现有简历定制，或提示用户先走 ②；
- 跨方向经历可以借用已确认事实，但每份简历只保留一个清晰定位，不揉成“通用版”，除非用户明确要求；
- 投递文件夹按 JD 所属方向放在`投递/<方向>/`下，没有对应方向的放`投递/未分方向/`；
- 目录名中的公司与岗位须能区分同名岗位，必要时加入部门、城市或招聘批次；
- 批量交付按方向分组，并附文件总清单，所有成稿分别完成事实与版式验收。
