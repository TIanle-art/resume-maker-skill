## 1. 何时使用

`career-claim-ledger.json`用于在方向简历、JD 定制、不同岗位版本和面试训练之间共享同一事实基线，解决多轮改写后证据、个人边界和确认状态丢失的问题。

账本是可选的，只在下面三种情况建，其余情况直接用简历和用户陈述即可：

- 出现“主导、负责人、Owner、0→1、核心作者”等强主张，面试中很可能被追问；
- 材料之间有冲突（GPA、时间、论文状态、指标或职责对不上）；
- 同一段经历要用于多个方向或多个岗位版本，需要保持说法一致。

用户主动要求建账本时照做。


## 2. 文件与最小结构

复制`assets/career-claim-ledger-template.json`到用户求职材料目录，替换全部虚构示例，不回写技能资产。每条`claims`记录至少保留：

| 字段 | 用途 |
|---|---|
| `id` | 稳定且唯一的主张编号 |
| `source_fact` | 用户原始事实，不做包装 |
| `candidate_wording` | 可用于简历或沟通的候选表述 |
| `sources` | 证据类型、位置、公开状态和必要说明 |
| `responsibility_level` | `参与`、`负责模块`、`主导方案或交付`、`项目负责人` |
| `verification_status` | `已确认`、`待确认`、`已过期`、`不采用` |
| `allowed_uses` | 允许进入的岗位版本或材料 |
| `interview_details` | 决策、困难、验证和结果等可追问细节 |
| `boundary` | 团队、个人、AI 与平台贡献的分界 |
| `risk_notes` | 冲突、缺口和成稿前必须处理的问题 |
| `last_verified` | 最近确认日期，未知为`null` |

`source_fact`不能为了配合新文案而被改写。新证据出现时更新来源和确认状态，不删除原始事实。

`sources`只保存定位证据所需的信息，如公开 URL、文件名、截图编号或“导师证明可提供”。不要复制密码、验证码、完整私人邮件、内部代码、客户数据或其他敏感内容。

## 3. 状态和使用规则

### 已确认

用户明确确认，或有其提供的可靠材料支持。可进入`allowed_uses`允许的正式材料，但仍须保留个人边界。用户确认不等于可以省略关键证据位置。

### 待确认

来源冲突、证据不完整或用户尚未确认。写进简历时带`【待确认】`标注，交付时向用户列出，由用户决定补全、删除还是保留。

### 已过期

曾经正确但会变化的信息，如年级、在读状态、论文在投状态、Star 数、当前职位。重新确认前不得作为当前事实使用。

### 不采用

已确认不准确、与当前岗位无关或用户不愿公开。可保留原因供内部复盘，不进入对外材料。

### 项目状态映射

- `【未完成】`、`【进行中】`、`【待实测】`、`【计划学习】`相关内容不得标为已确认完成；
- 部分完成时拆小主张，只核实已完成动作；
- 实测结果和预期目标分别记录，不用目标值冒充实测值；
- 原型、试点、生产落地和计划分别记录交付状态。

### 匹配状态（② 差距分析与 ③ 匹配分析共用，唯一定义）

| 状态 | 含义 | 能否当作已具备写进简历 |
|---|---|---|
| `已匹配` | 有明确、可展开的事实或作品证据 | 可以 |
| `表达缺口` | 用户确实做过，但材料没清楚呈现 | 可以（需改写表达） |
| `证据不足` | 材料暗示可能具备，但不足以支撑对外强表述 | 不可以，先补证据或降级表述 |
| `真实缺口` | 现有事实明确不满足，或用户确认尚未具备 | 不可以，如实告知 |
| `待确认` | 缺少决定性信息，不能替用户猜测 | 不可以，先问清 |

其他文件只引用这五个词，不使用“已具备”“已符合”等别名；需要更细的原因时写进`risk_notes`，不新建状态。

## 4. 冲突与开源贡献

同一事实出现多个版本时，不创建两个相互矛盾的“已确认”主张。保留一条记录，将不同来源写入`sources`，状态设为`待确认`，在`risk_notes`中列出需要统一的材料。

开源贡献须分别记录：

- 原仓库和具体版本；
- 用户实际修改范围；
- 测试、演示、Issue 或 PR 链接；
- PR 未提交、协作中、已合并、已发布等真实状态；
- 原作者与平台完成的部分；
- 许可证和公开边界。

Fork、下载、运行 Demo 本身不能生成“主导开源项目”的主张。

## 5. 校验和交付检查

创建或更新后，在支持 Python 3 的环境运行：

```bash
python3 <技能目录>/scripts/validate_claim_ledger.py <用户目录>/career-claim-ledger.json
```

需要机器可读结果时追加`--json`。脚本只检查结构、枚举、日期和确定性状态矛盾，不验证经历是否真实，也不联网确认 PR。

交付前检查：

- 每个强主张都能回指账本记录；
- 正式材料不含待确认、已过期或不采用主张；
- 团队成果没有自动变成个人成果；
- 指标保留口径、基线、周期和来源；
- 带标注的内容没有被自行改写成已完成；
- 账本不含密码、验证码和不必要的敏感材料；
- 修改候选措辞时没有篡改原始事实。
