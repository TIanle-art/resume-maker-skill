# 投递记录

## 本环节的定位

**本环节是投递台账**：维护一份`投递记录.md`，记下每家公司投了哪个岗位、用的哪版简历、进展到哪一步、下一步要做什么。

它不是流程的终点阶段，而是横跨全程的台账：③ 每产出一份定制稿加一行，④ 每次面试后更新状态，⑤ 的复盘结论再倒推回 ①／②／③／④。它也是判断「哪个方向、哪版简历更有效」的唯一明细来源（档案里只记汇总）。

用户说「使用投递记录 skill」时即指本环节。

## 1. 文件结构

`投递记录.md` 分三部分：

**总表**（一家公司的一个岗位占一行）：

| 公司 | 岗位 | 方向 | 类型 | 城市 | 渠道 | 投递日期 | 简历版本 | 状态 | 下一步与日期 | 薪资信息 | 备注 |
|---|---|---|---|---|---|---|---|---|---|---|---|

- **类型**：校招 / 实习 / 社招
- **渠道**：官网 / 招聘平台 / 内推 / 猎头 / 校园招聘会等
- **简历版本**：填定制稿的版本号，如`v2`，对应`投递/<方向>/<公司>-<岗位>/定制简历-v2.docx`；公司和岗位已在同一行，不需要另编 ID。直接用目标简历或其他文件投的，填文件名
- **状态**：只用这些固定值，便于统计——待投递、已投递、笔试或测评、一面、二面、三面及以上、HR 面、等待结果、已获 offer、已接受、未通过、已放弃。`assets/application-tracker.html`使用完全相同的枚举；导入旧版记录时会把“简历已投递、投递成功、HR面、Offer、拒绝”等别名归一到上述值，不另行创造状态。
- **下一步与日期**：如「11 月 20 日 14:00 二面」「等通知，11 月 25 日未回复则跟进」
- **薪资信息**：JD 上的范围或沟通中得知的数字
- **投递日期**：使用`YYYY-MM-DD`；需要记录具体时间时写成`YYYY-MM-DD HH:mm`，没有信息时留空，不用导入当天代替
- **备注**：记录岗位链接、反馈或其他补充信息；旧版没有“备注”列的 11 列表格仍可导入

**各公司备注**：每家公司一小节，按时间记录关键事件（投递、每轮面试的日期和要点、对方的反馈、待办）。面试的详细复盘写在 `投递/<方向>/<公司>-<岗位>/面试准备.md` 的 `## 训练记录` 里，这里只记一两句。

**更新记录**：日期加一句话。

## 2. 操作

每次操作都需要用户提供当前的 `投递记录.md`（附件、粘贴或在已连接的文件夹里）。没有就新建一份。不要凭记忆重建之前的记录。

- **新增**：用户说投了或准备投某个岗位时加一行。能从 JD、定制简历或匹配分析里读到的信息直接填，读不到的留空，不要猜。
- **更新**：用户说有进展时改状态、下一步，并在该公司备注里记一笔。用户一句话里提到多家公司时一并更新。
- **批量导入**：用户给出一批已投的岗位（文字、截图或表格）时，整理成总表。
- **查看**：给出进度汇总（见下节）。

日期按用户说的记；用户说「今天」「昨天」时换算成具体日期。每次修改后交还完整的新版文件，回复里用一两句话说明改了什么。

用户有已连接的文件夹时，直接读写其中的 `投递记录.md`。

### 使用本地可视化跟踪器

`assets/application-tracker.html`可与主记录直接同步，`投递记录.md`始终是主文件：

1. 将该 HTML 复制到用户输出目录，用浏览器打开。不得把真实记录写回技能资产；`assets/application-tracker-overview.svg`仅供预览。
2. **覆盖导入**：选择`投递记录.md`或 JSON 备份，确认后替换当前浏览器中的记录与文档。Markdown 总表支持上述 12 列，也兼容旧版 11 列；异常行逐行报告，不因单行错误丢弃其他有效记录。
3. **合并导入**：按“公司、岗位、方向、类型、城市、渠道、投递日期”识别同一条投递，避免误并不同城市或招聘批次的同名岗位。合并时保留当前文档的“各公司备注”和“更新记录”；当前没有文档时才沿用导入文档。
4. **导出 MD**：编辑后导出完整的新版`投递记录.md`。若文档来自导入，只替换“总表”章节，其他章节保持原文；随后按正常流程把完整文件交还给用户。
5. **备份 JSON**：新版备份同时保存记录和原 Markdown 文档；旧版纯记录数组仍可导入。CSV 只用于表格查看，不作为主记录或回填来源。
6. 数据仅保存在当前浏览器的本地存储中，换浏览器、设备或清除站点数据后可能不可见，应及时导出 MD 或 JSON。存储失败时不提交新增、修改或删除，先导出备份并检查浏览器权限或空间。

需要验证跟踪器时，在支持 Node.js 的环境运行：

```bash
node --test <技能目录>/scripts/test-application-tracker.mjs
```

## 3. 进度汇总

用户问「现在什么情况」「有什么要做的」时，在回复里简短给出：

- **各状态的数量**：已投递、面试中、已获 offer、未通过各多少
- **近期待办**：按日期列出接下来的面试、笔试和截止日期
- **需要跟进的**：投递或面试后较长时间没有消息的（默认投递后两周、面试后一周），提醒可以询问进展
- **即将到期的 offer**：有答复期限的要提醒

## 4. 复盘分析

记录积累到一定数量（大约十条以上）或用户要求时，分析：

- **各方向的转化**：每个方向投了多少、进入面试多少、拿到 offer 多少
- **卡在哪一步**：简历筛选、笔试、专业面、主管面还是 HR 面
- **渠道与简历版本的差异**：哪种渠道、哪版简历的回复更多

然后指出应该回到哪一步调整：

- 投了很多但很少进面试 → 简历或方向的问题，回到 ③ 重新定制，或回 ② 重审目标简历
- 经常进面试但过不了专业面 → 专业能力或项目深度的问题，回到 ④ 面试准备，或回 ② 重新规划项目
- 某个方向整体没有回音 → 可能要重新评估方向，回到 ① 方向选择

样本少时要说明结论不稳，不要从三五条记录里下强结论。只讲记录里能看出来的，不猜测公司拒绝的原因。

## 5. offer 对比

用户有两个及以上 offer，或要在 offer 与继续面试之间取舍时，做一张对比表：

| 项目 | offer A | offer B |
|---|---|---|

对比项：

- **薪资构成**：月基本工资、发薪月数、绩效与年终奖（注明固定还是浮动）、股票或期权（数量、归属年限）、签字费、补贴、五险一金基数与比例
- **第一年总收入估算**：用计算工具算，写清算法和假设；浮动部分给保守和乐观两个数；期权等价值不确定的部分单列，不计入确定收入
- **非薪资因素**：城市与生活成本、工作内容与成长、平台与稳定性、工作强度、与求职档案中偏好的契合度
- **还没问清的项**：列出来提醒用户去确认

用户没提供的数字留空并提醒补充，不要估。给出各自的优劣和与用户偏好的契合情况；选哪个由用户决定。这是信息整理，不是法律或财务意见；涉及合同条款（竞业限制、违约金、服务期）时提醒用户仔细阅读原文，必要时咨询专业人士。

## 6. 注意

- 只记用户告知的事实；状态不确定时问一句，不要替用户推断「应该是挂了」
- 记录里可能有联系人姓名、电话、薪资等私人信息：只用于这份记录，不要写进其他会对外分享的文件
- 用户需要可排序筛选的表格版本时，可从跟踪器导出 CSV；CSV 不是主记录，`投递记录.md`仍作为主文件保留
- 本地可视化跟踪器的导入、合并、导出和备份按第 2 节执行，真实数据只写入用户输出目录
